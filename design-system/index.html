Mutant X

The design system behind Kudos Portal, Pollinator, People Tracker and Demand Tracker. One warm neutral ground, one orange accent, San Francisco throughout, and a component set built for dense operational screens that still have to feel human.

Introduction

Mutant X is not a theme. It is the set of decisions that stop five product teams from each inventing their own idea of what a row, a field or a warning looks like. Everything in it was extracted from shipping screens, so nothing here is aspirational — if it is on this page, it exists in production.

What is in the box

Two CSS files

`mx-tokens.css` holds every value. `mx-components.css` holds every class and reads only from tokens. Ship both; retheme by editing the first.

One icon sprite

68 line icons on a 24×24 grid, 1.7px stroke, drawn to sit on the same optical weight as SF Pro at 13px.

A machine-readable export

`tokens.json` for Style Dictionary, Figma Variables, Tailwind or whatever the platform team lands on.

Installing

Setup 
<!-- order matters: tokens first, components second -->
<link rel="stylesheet" href="/mx/mx-tokens.css">
<link rel="stylesheet" href="/mx/mx-components.css">

<!-- the sprite, inlined once near the top of <body> -->
<div hidden>…contents of icons.svg…</div>

<!-- opt any subtree in -->
<body class="mx-scope" data-motion="auto">

`.mx-scope` sets the type stack, the box model and the focus ring. `data-motion` takes auto (follow the OS), on or off — see Motion.

Principles

Five rules that settle most arguments before they start. When a new component is proposed, it gets checked against these.

1 · A border plus one ambient shadow. Never a floating card.

On a warm ground, a shadow with no border reads as a rendering artefact. Every raised surface in Mutant X carries a 1px hairline and, at most, one soft shadow. The shadow says how far above the page it sits; the border says it is a real object.

2 · State is never carried by colour alone.

Every status pill pairs a hue with a dot shape — round for healthy, rotated square for warning, square for critical, bar for idle. It survives a greyscale print, a projector and deuteranopia. If you are adding a state, you are adding a shape.

3 · The label is a promise; the placeholder is not.

A placeholder disappears the moment someone types. Any field whose meaning is not obvious from its value keeps a visible label. The one exception is a single-field form where the question is the whole screen — see the ideal state on Text input.

4 · Columns leave in the order a reader would give them up.

Tables do not truncate and they do not scroll sideways. Each column carries a priority, secondary columns drop out at named widths, and below 820px the whole table becomes a list of stacked records with visible field labels. The drawer still holds everything.

5 · One owner per decision.

Sticky offsets come from --mx-sticky-h, nowhere else. Z-index comes from the layer ladder, nowhere else. Motion has one switch. The moment two places own the same number, they drift, and the bug is invisible until a customer finds it.

Token architecture

Three tiers. A component never reads tier 1 directly — it reads a semantic alias, so the product can be rethemed without opening a component file.

The three tiers
Tier 1 · Primitive

A raw value with no opinion about where it is used.

--mx-accent-550: #EC873A
Tier 2 · Semantic

A role. Points at a primitive. This is what components consume.

--mx-text-link: var(--mx-accent-650)
Tier 3 · Component

Scoped to one component, for values that genuinely have nowhere else to live.

--mx-field-indent: 18px

Accent · Mutant orange

The accent does four jobs and no others: it marks what is selected, it marks what is interactive, it draws the eye to the one primary action on a screen, and it tints the row under the pointer. Use it for a fifth thing and it stops meaning any of the four.

Contrast--mx-accent-550 at 4.5:1 against white fails. It is a fill colour — white text on it passes at 3.4:1 for large text only, which is why buttons using it run at 12.5px/650 minimum and carry an icon. For accent-coloured text, use --mx-accent-650 (4.6:1) or --mx-accent-750 (5.9:1). Never set --mx-accent-550 as a text colour on a light ground.

Typography

San Francisco, Apple's system family, throughout. It is the right call for a dense operational product: it was drawn for exactly this — small sizes, tight leading, numerals that line up in a column — and on Apple hardware it costs zero bytes.

Optical sizes are automaticSF Pro ships two optical cuts. Using -apple-system lets the OS switch from SF Pro Text to SF Pro Display at 20px, which is what you want: Display has tighter apertures and tighter default tracking, Text has open counters that stay legible at 12px. Do not name a cut explicitly unless you are deliberately overriding that switch. On Windows and Android the stack falls to Segoe UI / Roboto — metrics differ by roughly 2–4%, so never build a layout that depends on a string being exactly one line.
Weights 550, 650 and 750 need the variable fontSF Pro on macOS and iOS is variable and resolves these exactly. Elsewhere the browser rounds to the nearest static weight — 650 becomes 600 or 700, and a whole table shifts. We set font-synthesis-weight: none so it degrades to a real weight rather than a smeared fake bold. If you are shipping to a mixed-platform audience and the shift matters, self-host SF Pro Variable under Apple's licence, or map 650→600 and 750→700 in your platform theme.

Prose measure

Body copy caps at 72 characters and uses text-wrap: pretty so a heading never ends on an orphan. Anything over 72ch in a dense UI stops being read and starts being skimmed — which is fine for marketing and fatal for an error message.

Rhythm

Three defaults carry most layouts. Reach for something else only when you can say why.

Icon to label, chip to chip, button to button: space-4 (8px).

Field to field, card to card inside a panel: space-6 (12px).

Region

Panel to panel, page gutter, modal padding: space-10 (24px).

Do

Don't

Raise a card on hover to signal it is clickable. Use .mx-anim-lift for that, which moves it 3px and changes the shadow — a static heavier shadow just makes the grid look uneven.

Iconography

68 line icons on a 24×24 grid, 1.7px stroke, round caps and joins. The stroke weight is not arbitrary — it was set to match the optical weight of SF Pro at 13px/650, so an icon beside a label reads as part of the same word rather than a decal stuck next to it.

Rules

  • Stroke is 1.7px at every size. Do not scale the stroke with the icon — scale the box. A 15px icon and a 25px icon carry the same line weight, which is what keeps a toolbar and a nav rail feeling like one product.
  • Colour comes from currentColor. An icon never carries its own fill. It inherits from the control it sits in, so hover, active and disabled states are free.
  • Sizes: 10–13px inside a chip, 15–16px beside a label, 17–19px in an icon button, 22px in a tile, 25px in the product rail.
  • Every icon-only control needs an aria-label. There is no exception, including the obvious ones.

Reduced motion — one owner, three states

Motion is controlled by data-motion on the root element. auto is the default and follows the operating system, so someone who asked for reduced motion in System Settings gets it without ever opening our preferences. Turning the switch is an explicit choice and wins over the OS hint in both directions — including someone who wants motion despite an OS-level reduction.

Implementation 
[data-motion="off"] *,
[data-motion="off"] *::before,
[data-motion="off"] *::after { animation: none !important; transition: none !important }

/* auto follows the OS; off stays off */
@media (prefers-reduced-motion: reduce) {
  [data-motion="auto"] * {
    animation-duration: .01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: .01ms !important
  }
}

Use the Motion switch in this page's header to cycle auto → on → off and watch the specimens below respond.

Container queries

A table inside a 70% panel is not the width of the viewport. Any table that lives in a split layout sets container-type: inline-size on its wrapper and responds to 910 · 1130 · 1330 instead. Getting this wrong is subtle and nasty: at a 1380px viewport the panel is ~1330px, so a viewport-keyed rule fires one breakpoint too late and the row silently overflows.

Hide the cell and the column togetherA priority class that hides a cell without also shortening --mx-cols knocks every subsequent cell in the row out of alignment with its header. Both rules go in the same media or container block, always.

Accessibility

Target is WCAG 2.2 AA. What follows is the part that is actually enforced in the component layer — the rest is on whoever assembles the page.

Focus

One ring, everywhere: 2px solid rgba(236,135,58,.6) with 2px offset, on :focus-visible only. Boxed controls add a 3px accent halo inside as well, because an outline alone gets lost against a border of a similar weight. Nothing in this system removes the outline without replacing it.

Two known failures, stated plainly
1 · text-4 as a placeholder is 2.7:1. Placeholder text is exempt from WCAG 1.4.3 as it is not "text content", but a placeholder that is the only label — the ideal state on Text input — is doing a label's job and inherits a label's obligation. Use it only where the surrounding heading already names the field.
2 · white on accent-550 is 2.6:1 and passes nothing. Primary buttons get away with it under 1.4.11 (non-text contrast, 3:1) because the button shape is the identified component, but the label itself is under-contrast. This is inherited from the brand and is on the roadmap — see Known drift.

State & semantics

  • Selected state is aria-selected on tabs and segmented controls, aria-pressed on toggle buttons and choice cards, aria-checked with role="switch" on toggles. The CSS keys off the ARIA attribute, so the two cannot drift apart.
  • Error state is .is-error on the field wrapper plus aria-invalid="true" and aria-describedby pointing at the message. The class styles it; the ARIA announces it.
  • Every overlay is role="dialog" aria-modal="true", labelled by its own title, closes on Esc, traps focus while open and returns focus to the trigger on close.
  • Toasts are role="status" — polite. Anything that must interrupt is not a toast; it is a banner or a dialog.
  • Sortable headers carry aria-sort of ascending / descending / none.
  • The live indicator's animation is decorative and carries no meaning that the adjacent text does not already state.

Text input

The signature component of Mutant X. It is an underline field: no box, no fill, one rule that carries the whole state machine. That choice is what lets a form sit directly on the page ground with nothing containing it, and it is why a Mutant screen reads lighter than the same screen built from boxed inputs.

Anatomy

Four parts, top to bottom
1 · LabelFlush left. 13px / 650 / --mx-field-label. Required mark is --mx-crit-signal. 2 · Control40px tall. Value 15px / 400, indented 18px so it sits inside the field rather than on top of the label. 3 · Rule1.5px at rest, 2px when focused or in error. Full width — the rule is the field boundary. 4 · MessageFlush left, 12.5px. Muted for help, --mx-crit-signal for an error.
Why the value is indented and the label is notAn underline field has no left edge to anchor against. Pushing the value in by 18px while the label stays flush creates a visible hierarchy in a component with no container — the label reads as the heading of a small block, the value reads as its content. Remove the indent and the two collide into one left-aligned column that is harder to scan down a form.

Live validation

Type into the field. Anything that is not exactly seven digits trips the error state on input and on blur.

Try it

Error, counter and tall

Variants
Counters count up, not down140 / 280, not 140 remaining. A remaining count reads as a budget and makes people write to the limit; a count up reads as a measure and makes them write to the point. Turn the count red only when it is over, and block submission at that point rather than truncating what someone typed.

Guidance

Do

Size the initial height to the expected answer. A 92px box invites a sentence; a 200px box invites a paragraph. If you want a paragraph, ask for one and give it the room.

Don't

Auto-grow past about eight lines. Beyond that the submit button leaves the viewport and people lose the thread. Let it scroll instead.

Rules

  • The row is the target. Clicking anywhere in the name cell opens the object. Row-level icon buttons are for actions that are not "open".
  • The name cell carries two lines. The human name in .mx-cell-strong, the machine identifier in .mx-cell-sub. Never make someone read an ID to find a display.
  • Numbers are tabular and right-aligned only when they are compared. An uptime column is compared; a version number is not.
  • The actions column is right-aligned, and so is its header.
  • Hover paints the whole row in accent-wash with a 3px accent edge at the left. Not a border — an inset shadow, so it does not shift the layout by a pixel.
  • Sticky headers read --mx-head-top from their wrapper. Never hard-code the offset.

Rules

  • One column. Two columns double the number of places an eye has to land, and every field in a two-column form is a candidate for being missed. Split only when the fields pair evenly and genuinely belong together — width and height, start and end date.
  • Required is the exception, not the rule. If nine of ten fields are required, mark the one that is not with optional and drop the asterisks.
  • Help text sits under the field, not under the label. Under the label it gets read as part of the question; under the field it gets read as guidance on the answer.
  • The primary action is last, on the right. Cancel is quiet and to its left. Never reverse this per screen.
  • Errors appear on blur, then live. Never on first keystroke. See Live validation.
  • A form that fails on submit moves focus to the first invalid field and shows a banner naming how many fields need attention.

Data visualisation

Charts follow the same rules as everything else: the point is the finding, not the picture.

Rules

  • The six categorical hues, in order. The mapping from KPI to colour is stable across every screen. Never re-map per chart.
  • No chart type that needs a paragraph to explain itself. A radar plot got replaced with ranked bars for exactly this reason — if the chart needs prose beside it to be readable, the prose is doing the work.
  • Rank when order carries meaning. A sorted bar list is itself the finding; an alphabetical one hides it.
  • One scale per axis, stated. A bar and a tick on the same track are comparable; two tracks with different maxima are not, however similar they look.
  • Axis labels are HTML, not SVG text. Absolutely position them over the chart box. SVG text does not scale predictably inside a responsive container, and interpolated content inside an SVG <text> node silently renders nothing in several template runtimes.
  • Line strokes stay 2.4px at every width. Scale the box, not the stroke.
  • Always give the raw number. A bar is a comparison aid, never the only place a value appears.
  • Sparklines carry a scale. Min and max at each end, or the line is decoration.

Do

18 nominations are waiting on you. The oldest has been open for 11 days. Numbers, consequence, and enough for someone to decide whether to act now.

You have pending items requiring attention! No count, no age, no consequence, and an exclamation mark doing the work a fact should do.

React — a component reads classes, not values 
export function Field({ label, required, error, help, ...props }) {
  const id = useId();
  return (
    <label className={`mx-field ${error ? 'is-error' : ''}`}>
      <span className="mx-field__label">
        {label}{required && <span className="mx-field__req">*</span>}
      </span>
      <input
        className="mx-field__control"
        aria-invalid={!!error}
        aria-describedby={error || help ? `${id}-msg` : undefined}
        {...props} />
      {(error || help) && (
        <span id={`${id}-msg`}
              className={`mx-field__msg ${error ? 'mx-field__msg--error' : ''}`}>
          {error || help}
        </span>
      )}
    </label>
  );
}

Definition of done

A screen is ready for review when every one of these is true. Not aspirational — this is the checklist.

Check
No hard-coded colour, size, radius, shadow or duration. Grep the diff for # and px.
Every interactive element reachable and operable by keyboard, in a sensible order.
Visible focus on everything focusable. Nothing sets outline: none without a replacement.
Every icon-only control has an aria-label that names the object it acts on.
Loading, empty, error and no-results states all exist and are distinguishable from each other.
Tested at 390 · 820 · 1180 · 1440 · 1920. No horizontal page scroll at any of them.
Tables drop columns by priority and shorten --mx-cols in the same rule.
Checked with prefers-reduced-motion: reduce and with data-motion="off".
Text contrast passes 4.5:1, or the exception is one of the two documented in Accessibility.
No status conveyed by colour alone — the dot shape or a word carries it too.
Long values tested: a 60-character name, a 6-digit count, an empty optional field.
Rendered on a non-Apple platform at least once — the weight fallback is checked, not assumed.

Adding a component

  1. Prove it does not exist. Most requests are an existing component with different content. A "notification card" is a feed card.
  2. Find it in two shipping screens. One instance is a screen, not a pattern.
  3. Build it from tokens only. If it needs a value the system does not have, that is the conversation — not a magic number in a component file.
  4. Ship all its states — rest, hover, focus, active, disabled, loading, empty, error. A component with three states is half a component.
  5. Write the "don't". The misuse you can already picture is the one that will happen.
  6. Add it here with a live specimen, the markup, and its token table.

Known drift

Honest accounting. These are places where the shipping product does not yet match this document. Writing them down is the difference between a design system and a mood board — a reviewer can hold us to a list, and a developer knows which inconsistency is a bug and which is a decision that has not been made yet.

IDIssueImpactProposal
DR-01Primary button contrast. White on accent-550 is 2.6:1 — below AA for text of any size.HighDarken the primary fill to accent-650 (#CE6B1F), which takes white to 4.6:1, and keep accent-550 for the hover. Needs brand sign-off.
DR-02Spacing drift. Shipping screens use 1, 3, 5, 7, 9, 11 and 13px gaps that are not on the scale.MediumSnap to the nearest even step during component migration. No visual review will catch a 1px change; a diff will.
DR-03Radius drift. 9, 11, 13, 14, 18 and 19px all appear in production alongside the seven canonical steps.MediumMap to the nearest token. 14px → lg, 9/11 → md, 18/19 → xl.
DR-04Z-index collision. The product rail and row menus both sat at 70 in the original stylesheet, so a menu near the rail could be covered.Fixed hereMenus moved to --mx-z-popover (95). Migrate consuming code.
DR-05Placeholder-as-label. The ideal field state relies on a 2.7:1 placeholder to carry the label.MediumRestrict to single-field screens where a heading already names the field, and darken the placeholder to neutral-750 (4.1:1) where it must be the label.
DR-06No checkbox or radio. No shipping screen needed one, so none exists.OpenAdd when a screen genuinely needs multi-select inside a form that has a Save button. Do not pre-build it.
DR-07No dark theme. The dark tokens represent rendered surfaces, not an alternative theme.OpenThe token architecture supports it — a dark theme is a second set of semantic aliases. It is a scoping decision, not a technical one.
DR-08Font weights 550/650/750 resolve exactly only where SF Pro Variable is available.MediumSelf-host SF Pro Variable under Apple's licence, or ship a platform theme mapping 650→600 and 750→700.
